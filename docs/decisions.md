# Decisions

What we decided and briefly why. Numbers are stable: append new decisions at the end, mark
superseded ones instead of deleting them. Paths are the current ones.

| # | Topic | Decision | Why |
|---|---|---|---|
| 1 | Engine | WebKit at a WPE release, own `PORT=Wasm` | Of the big engines WebKit ports best (CLoop, curl backend, generic RunLoop) |
| 2 | Process model | Single process in a Web Worker | Rebuilding WebKit2 IPC in WASM would be a lot of work and slower (copies instead of shared memory) |
| 3 | Port base | Structure like the PlayStation port, graphics like WPE (Skia) | PlayStation = curl + RunLoopGeneric + static, without GLib/libsoup. A slimmed WPE would have to cut out GLib, soup and WebKit2 |
| 4 | JS | JSC CLoop, no JIT | WASM cannot run a normal JIT. CLoop is an official, tested mode |
| 5 | Memory model | wasm32 (no Memory64) | Memory64 is clearly slower. 4 GB are enough with trimmed features |
| 6 | Graphics | Skia, CPU first, then WebGL 2 | WebKit no longer supports Cairo. Skia is proven in WASM (CanvasKit) |
| 7 | Network | Wisp over WebSocket to our own relay | Browsers have no raw TCP/UDP, `fetch()` fails on CORS. Wisp carries TCP and UDP (WireGuard later) |
| 8 | TLS | OpenSSL inside WASM | End-to-end encrypted, the relay sees no content. The WebCore curl backend needs the OpenSSL API |
| 9 | Threads | Emscripten pthreads, no Asyncify | Asyncify makes the code much bigger. Maybe JSPI later |
| 10 | Target browsers | Chrome/Chromebook first, then Firefox, Safari optional | Project goal; Chrome has the best WASM support |
| 11 | Fetching WebKit | Script with shallow + sparse + blobless fetch instead of a submodule | A submodule pulls GBs of tests. This way about 300 MB |
| 12 | Build | GitHub Actions with a Docker toolchain image | Public repo, same environment locally and in CI |
| 13 | Reference | WebkitWasm (theogbob) as reference only, no fork | We want a clean, reproducible base. BSD-2-Clause, taking code is allowed with the copyright notice ([licensing.md](licensing.md)) |
| 14 | License | BSD-2-Clause for our own code | Compatible with WebKit (LGPL/BSD) and the reference |
| 15 | Meson | From pip (pinned) instead of the Ubuntu package | fontconfig 2.17 needs Meson >= 1.6.1, Ubuntu 24.04 has 1.3 |
| 16 | ICU data | Built ourselves from the host archive as `libicudata.a` | In a cross build ICU builds only stub data |
| 17 | GC roots (superseded by #36) | `--spill-pointers` for the whole binary | Without it live objects get lost (proven with a stress test) |
| 18 | First JSC build | `PORT=JSCOnly` with patches, own `PORT=Wasm` only for WebCore | JSCOnly is enough for JSC and keeps the patches small |
| 19 | Spill and names | `--spill-pointers` needs `--profiling-funcs` | Without names the pass cannot find the stack pointer after full optimization |
| 20 | Link flags of jsc | Only on the target `jsc`, not global | The LLInt extractors (linked with -O0) do not survive `--spill-pointers` |
| 21 | Theme | Adwaita (like the Windows port) | Ready form controls and scrollbars without dependencies |
| 22 | Clients | Make the empty clients overridable by patch (`final` -> `override`) | Mechanical patch; our clients override only what is needed |
| 23 | Event loop | Pump the RunLoop from outside (wake-up callback + timer for the next WebCore timer) | A worker must not block, otherwise no messages arrive |
| 24 | Frames to the host (superseded by #83) | Pixels in shared memory, host copies with putImageData, one frame in flight | Simple and robust until the GPU path |
| 25 | UI (superseded by #199) | Plain HTML/CSS/JS without a build step instead of TypeScript + Vite | No npm dependencies, easier hosting, enough for the UI |
| 26 | Compositing (superseded by #94) | No accelerated compositing, empty `GraphicsLayerWasm` | Everything paints into the pixel buffer; enough until the GPU path |
| 27 | Exceptions | Allow throwing at link time, not catching | Dependencies (C++) reference `__cxa_throw`. A throw aborts, as WebKit expects |
| 28 | CA certificates (superseded by #162) | Mozilla bundle in the data package, optional `extra-ca.crt` | Company networks with their own CA, local tests behind a TLS proxy |
| 29 | ICU data | Filter with `icupkg -r` instead of rebuilding from source | The source archive has only the finished `.dat`. Filtering converters and languages saves 14 MB |
| 30 | Delivery | Engine per version in its own folder, cached immutable, precompressed `.br` | Never an old .wasm from a cache; Brotli q11 once at deploy instead of per request |
| 31 | Text input | Hidden `<textarea>` instead of focus on the canvas | Only this way dead keys, IME and on-screen keyboards arrive as finished text |
| 32 | Popups | The engine opens the view itself (ids from 2^20), the UI makes a tab of it | `createWindow` must return a Page synchronously |
| 33 | Downloads (superseded by #163) | Load the file again with an own CurlRequest, data to the UI | Simpler than rehanging the running load; the URL is already the target after redirects |
| 34 | Storage (superseded by #142) | IDBFS (JS file system) instead of OPFS/WasmFS | WasmFS had no sockets and our network used SOCKFS (no longer since #68) |
| 35 | localStorage/IndexedDB | Build the files of `WebKitLegacy/Storage` | Finished, tested implementation (InProcessIDBServer, StorageAreaSync) |
| 36 | GC roots (engine) | GC only on an empty stack (DeferGC around every task, patch 0012) instead of `--spill-pointers` | The pass made everything about 10x slower and the .wasm 34 MB bigger. Covered by a stress test (crash without deferral) |
| 37 | Fonts | Generate the fontconfig cache at build time, font folders get mtime 0 | fontconfig then trusts the cache and does not rescan the fonts at every start |
| 38 | Missing Content-Type | Sniff like other browsers (extension, else HTML) | Otherwise the page was treated as a download |
| 39 | WebSockets | `WebSocketChannel` + `SocketStreamHandle` copied from WebKitLegacy (`engine/src/websocket/`), own socket on WebCore's `CurlStreamScheduler` | WebCore has no single-process WebSocket channel any more; WebKitLegacy only a CFNetwork one |
| 40 | Video | `ENABLE_VIDEO` on (playback see #46) | Pages expect the media API (`video.pause()` etc.) |
| 41 | Web Audio | The engine renders on its own thread into a ring in WASM memory, an AudioWorklet of the host plays it | No copies over postMessage, no lock; the worklet reads shared memory directly |
| 42 | Audio decoder | `decodeAudioData` through an `OfflineAudioContext` of the host | All formats of the browser, without ffmpeg in WASM |
| 43 | FFT | Own small radix-2 FFT instead of a library | WebCore otherwise only has vDSP (Apple) or GStreamer; enough for Web Audio sizes |
| 44 | Favicons | The engine loads the icon and sends the bytes to the host | The host has no network of its own (everything goes through the relay); cookies come along |
| 45 | Fullscreen | The whole view area goes fullscreen, not a single element | The engine paints everything into one canvas; WebCore lays the element over the page itself |
| 46 | Video playback | A host `<video>` plays, the engine paints the copied frames | All codecs of the browser, sound directly. Copying frames costs some CPU, but overlays, clipping and scrolling are exact |
| 47 | Video data | A service worker asks the engine in chunks (Range, 2 MB) | The host has no network; the next chunk comes only when the browser reads, so memory stays small |
| 48 | MSE | WebCore MSE with own parsers (timestamps only), data also to a MediaSource of the host | `buffered`, seeking and events follow the standard, decoding stays with the browser |
| 49 | Aligned memory | WTF rounds the size of `aligned_alloc` up to a multiple of the alignment (patch 0015) | Emscripten returns nullptr otherwise (C11 rule) and WebKit crashes, for example loading HRTF |
| 50 | WebKit bug in `VectorMath::multiplyComplex` | Store the result in a temporary first (patch 0013) | The non-SIMD code overwrote the real part too early, FFT convolution (ConvolverNode, HRTF) was wrong. Hidden on x86/ARM where SIMD computes |
| 51 | WebGL | No ANGLE in WASM, GL calls go to Emscripten's GLES (host WebGL in the engine worker) | ANGLE in WASM would be huge and end up calling WebGL anyway. The browser validates shaders and limits itself |
| 52 | WebGL version | A WebGL 1 page gets a WebGL 1 host context, WebGL 2 a WebGL 2 context | Without ANGLE's shader translator the shader language must match exactly |
| 53 | ANGLE functions | Generated from the Khronos headers by `tools/gen-angle-shim.py`, the rest by hand | About 300 functions, nearly all 1:1. Regenerate on a WebKit update |
| 54 | Many WebGL contexts | One host context per WebGL version, state saved and restored on switch | Chrome allows only 4 contexts per worker. Fingerprinting and feature tests create short-lived contexts that would kill the page's |
| 55 | Image encoders | Skia encoders on (PNG, JPEG, WebP) | Without them `toDataURL`/`toBlob` always gave `data:,`. The libs were in the sysroot already |
| 56 | WebAssembly of the pages | Modules run in the browser's WASM engine, API rebuilt in JSC | JSC cannot run WebAssembly without JIT. An interpreter in WASM would be 20-50x slower |
| 57 | Module memory | Rewrite the module: its memory is a region of the engine memory, every access bounds-checked | JSC must show `memory.buffer` as a normal ArrayBuffer inside engine memory. The check keeps each module in its region |
| 58 | Base and size in code | In locals per function, reloaded after calls | Reading imported globals at every access was about 3x slower, this costs about 12 % |
| 59 | WebAssembly API | Evaluated on first access (getter on the global object) | Most pages never use WebAssembly and pay nothing |
| 60 | GC during long scripts | Own VM trap, collected only in the interpreter at `op_check_traps` and only without nested C++ | There all values are in memory, not in WASM locals. First page: peak 443 instead of 531 MB. `--spill-pointers` would be 14x slower again |
| 61 | Releasing memory | `WebCore::releaseMemory` automatically from 192 MB used, not only on memory pressure | WASM memory never shrinks and the browser reports no memory pressure. Costs about 0.3 s, so at most every 5 s and after 64 MB growth (trigger see #64) |
| 62 | Call caches in the interpreter | `forceICFailure` off on WASM (patch 0019) | On 32 bit it is on by default but only matters for JIT code we do not have. The interpreter caches work on 32 bit; without them every call detoured through C++ |
| 63 | Skia on WASM | SSE4.1 path through Emscripten's SSE mapping to WASM SIMD (patch 0020) | The scalar pipeline paints one pixel per step. SSE4.1 halves paint time; an own WASM SIMD path would be much more work |
| 64 | Memory release trigger | Growth of `malloc_footprint()` instead of used memory | Free to read and hits exactly the moment WASM memory would grow |
| 65 | TLS ciphers | ChaCha20-Poly1305 before AES-GCM, also for TLS 1.3 | Without AES hardware ChaCha20 is about 4x faster in software. WebKit only set the TLS 1.2 list, TLS 1.3 used OpenSSL's default (AES-256-GCM first) |
| 66 | WebCrypto | Fix the OpenSSL 3 bugs in WebKit's code instead of an own implementation | Only two small places (AES-GCM order, RSA macro checks). AWS WAF checks (SBB, IMDb, Booking) pass |
| 67 | SQLite files | Own VFS in WASM memory, whole files written (since #142 to OPFS on the engine thread, replaced atomically; since #180 only the database with the WAL folded in) | Every file access went synchronously through the main thread (Emscripten's JS file system) |
| 68 | Sockets | Own layer in WASM (`--wrap` at link time) instead of Emscripten's SOCKFS | No synchronous detour through the main thread for every send/recv/poll. Transport stays replaceable (WireGuard). No curl patch |
| 69 | Main thread and locks | Nothing that can wait under a lock on the main thread | While waiting on the main thread Emscripten runs its queue; that caused self deadlocks (nzz.ch, 20min.ch hung now and then) |
| 70 | HTTP cache | Cache API of the host instead of files in IDBFS. Counts only its own content (`x-bl-size`), limit 400 MB and at most a quarter of the quota, trimmed to 80 % beyond. HTTP/1 responses that end only with the connection are not stored. Lookup and revalidation for all loaders see #182 | IDBFS loaded everything into memory at start and wrote the whole tree every 5 s. The Cache API stays on disk and is read on demand |
| 71 | WebKit bug in the C loop stack limit | `StackManager::cancelStop` resets the JS stack limit in the C loop, not the native one (patch 0022) | After the first VM trap the interpreter checked against the wrong limit; deep recursion wrote past the JS stack (crash on x.com, broken GC mark stack). Test: `tests/engine/pages/stack.html` |
| 72 | GC during long scripts (addendum to #60) | Also collect at function entry (slow path of the stack check), not only at `op_check_traps` | A trap sets the stack limit so the next call lands in the slow path, where the trap was dropped. On real pages the GC almost never ran (CNN: 0 instead of 6 times) |
| 73 | Ed25519/X25519 in WebCrypto | Own OpenSSL code (`EVP_PKEY_ED25519/X25519`, patch 0010) | WebKit only has Apple and libgcrypt code. With EVP it is three small files; OpenSSL is there for TLS anyway |
| 74 | Virtual memory under Emscripten | `tryLargeZeroedMemalignVirtual` and `OSAllocator::zeroFill` with `aligned_alloc`/`memset` (patch 0023) | Emscripten cannot release parts of a mapping and has no `MAP_FIXED`. Resizable ArrayBuffer crashed (`new ArrayBuffer(n, {maxByteLength})`) |
| 75 | WebCore settings | Enable everything WebKit browsers (WPE/GTK/Safari) enable that needs no backend of its own | Defaults for "WebCore alone" are often `false`. About 30 finished features came in (Navigation API, date/color inputs, Compression Streams ...) |
| 76 | Pickers (`<select>`, color, date) | `<select>` as an own list in the UI, color/date through a hidden host field with `showPicker()` | The list must fit keyboard and window; for color/date the real system dialog beats a replica. Now `@browser-lite/ui` |
| 77 | Yardstick | A page with feature checks runs in the host Chromium and in browser-lite, differences as a list, a stored list guards against regressions | Shows objectively how close we are to Chromium and what is missing next |
| 78 | Feature switches | Drag support, touch, gamepad, notifications, geolocation, pointer lock, OffscreenCanvas, variable fonts, Media Session, speech synthesis on at once | Every switch rebuilds all of WebKit; the host binding lives in `engine/src` (fast to build) |
| 79 | Permissions (storage superseded by #206) | Own prompt in the UI, decision per origin of the top page (notifications per own origin). `camera-microphone` covers both, `permissions.query` returns the remembered decision, a tab closed with an open question remembers nothing | Like Chrome. The host browser asks for browser-lite only once (location, notifications for the whole app) |
| 80 | Touch | Touch events to the page, scrolling/click only when the page does not call `preventDefault` | Maps and games with own touch logic work, normal pages scroll as usual |
| 81 | `ontouchstart` | Only when the host reports a touchscreen (`navigator.maxTouchPoints`) | WebKit otherwise always says "touch" (except GTK) and many pages show the mobile view |
| 82 | Session | Background tabs load on first click | With the interpreter every page costs a lot of time and memory. Chrome does the same |
| 83 | Showing frames | Each view canvas goes with `transferControlToOffscreen` to the engine's worker, the engine paints into it | The main thread copied every frame and waited up to 1.7 s for the compositor, and every engine call through the main thread waited too. CNN: engine waited 0.5 instead of 4.5 s, load 19.8 -> 16.2 s |
| 84 | Waiting for the main thread | Remember answers instead of asking again: Skia font checks, `canPlayType`, `access()` on fixed files; one shared crypto queue (patch 0024) | Skia read whole font files through the JS file system on every lookup, every iframe started its own thread for `window.crypto`. 3.5 s waiting on CNN |
| 85 | Allocator | dlmalloc stays, mimalloc tested | mimalloc was slower (CNN hit the time limit). dlmalloc's lock costs only about 0.2 s while loading |
| 86 | GPU raster | Skia (Ganesh) paints through WebGL 2 in the engine worker, one shared context, frame via `transferToImageBitmap`. On by default, `engine.gpu: false` turns it off; without WebGL 2 or after context loss CPU (back to GPU after restore, #157) | Gradients, scaled images, shadows and text cost almost nothing on the engine thread. Even with SwiftShader scrolling: NZZ 1226 -> 481 ms, GitHub longest frame 481 -> 184 ms |
| 87 | Skia GL context | Every Skia GL call first checks that its context is current (wrapper in Skia's WebGL interface, patch 0020) | Skia calls GL while painting, and WebGL canvases switch the context mid-paint. Switching only on flush gave white WebGL frames and a crash on CNN |
| 88 | Engine thread tasks | Own list instead of Emscripten's queue; a pass runs only what was queued at its start, then back to the event loop (MessageChannel) | Emscripten drains the queue while more arrives, but an OffscreenCanvas frame only appears at the end of the JS task: GitHub stayed white 10 s, now 5 s and updating |
| 89 | More web APIs | Canvas filters, `moveBefore`, `select.showPicker`, `scrollbar-color`, Storage API, Screen Orientation, Wake Lock by setting; own StorageProvider and ScreenOrientationManager (`engine/src/WebPlatformExtras.cpp`) | Finished in WebKit, only the browser side was missing. Yardstick 217 -> 228 of 277 |
| 90 | Polyfills | `scheduler.postTask/yield` (+ `TaskController`) and `navigator.vibrate` as a user script before every page script | Chromium has them, WebKit not. Only APIs with clear meaning that can be rebuilt cleanly; no Chrome identity (`userAgentData`; `connection` and `deviceMemory` yes, with host values, #120) |
| 91 | Links in a new tab | Ctrl/Cmd+click and middle click caught in the engine's navigation policy, background tab like Chrome | WebKit reports both as a link click with button/modifiers |
| 92 | View source | The engine loads the address like a download (same cookies), the UI shows the text with line numbers | WebKit has no view-source mode; this shows exactly what the server sent |
| 93 | Cache API | Own `CacheStorageConnection` in the engine for all views, separated by origin (`engine/src/CacheStorageWasm.cpp`); persistent since #105, bodies as files since #155 | WebKit implements it only in the WebKit2 network process |
| 94 | Compositing with layers | WebKit's Coordinated Graphics like WPE (GraphicsLayerCoordinated, SkiaPaintingEngine, SkiaCompositingLayer), since #98 on an own compositor thread (`engine/src/LayerTreeHostWasm.cpp`). On when WebGL 2 works, `engine.compositing: false` turns it off, after GPU loss no layers | SwiftShader: NZZ scrolling 6 slow frames -> 0, GitHub 1946 -> 701 ms; loading CNN 17.2 -> 14.5 s. `transform`/`opacity` animations, `will-change`, fixed elements and scrolling only composite. Tiles paint on CPU threads, CSS filters on the GPU. Patch 0025 adapts the EGL parts to WebGL (RGBA, context before each call) |
| 95 | Origin Private File System | Own `FileSystemStorageConnection` on the engine thread (`engine/src/FileSystemStorageWasm.cpp`), files under `/data/opfs/<origin>/` | WebKit2 has it in the network process. Same rules (names, locks, errors); `createWritable` writes a copy under `/data/opfs-swap`, `close()` renames it over the file, leftovers are deleted at start; `move()` fails while source or target is locked |
| 96 | `requestVideoFrameCallback` | Setting on, `MediaPlayerPrivateWasm` reports size, media time and frame number per new frame | Chromium has it, video sites use it for subtitles and effects |
| 97 | Orientation/motion sensors (completed by #102) | Clients and host events ready, the WebKit switch comes with the next full rebuild | A switch in `OptionsWasm.cmake` does not change the local CMake cache; untested it stays out of CI |
| 98 | Compositor thread | Own pthread with its own WebGL 2 context composites and presents; the view canvases belong to its worker (`engine/src/Compositor.cpp`). The engine thread does rendering update and flush, the compositor takes over at its worker's next rAF | CSS animations keep running while page JS blocks the engine thread. Basis for async scrolling |
| 99 | GL objects and threads | BitmapTexture deletes textures/framebuffers through the engine (`bl_texmap_gl_delete`), which forwards to the context's thread | WebGL ids are valid only in the worker that made them; deleting on the engine thread would hit a foreign texture with the same number |
| 100 | GPU loss with layers | The engine ends compositing in all frames itself (`clearBackingForAllLayers`, `enableCompositingMode(false)`) | The setting alone acts only at the next style/layout change; the page stayed white until then |
| 101 | Async scrolling | WebKit's scrolling tree like WPE (`ENABLE_ASYNC_SCROLLING`, `SCROLLING_THREAD`, `KINETIC_SCROLLING`, `WHEEL_EVENT_REGIONS`). Wheel and swipe events go from the host through the compositor thread to WebCore's scrolling thread (`engine/src/ScrollingWasm.cpp`); the engine thread gets them only where the page has a blocking `wheel` listener. `BL_ASYNC_SCROLLING=0` turns it off | Scrolling stays smooth while page JS blocks (test: 5 s endless loop, the page still scrolls). The compositor sends a display tick after each wheel event and during smooth scrolling because WebKit applies scrolling thread positions only at the next display refresh. That tick counts as wheel activity even when it comes later than the 50 ms WebKit allows for it (slow machine), otherwise the position waited for the engine thread |
| 102 | Orientation/motion sensors (addendum to #97) | `ENABLE_DEVICE_ORIENTATION` on, with #101 in one full rebuild | `deviceorientation`/`devicemotion` of the host reach the visible view while the page listens |
| 103 | Service workers and SharedWorker | WebCore's SWServer, SWClientConnection and SWContextManager on the engine thread, connected without IPC but always through the RunLoop (`engine/src/ServiceWorkerWasm.cpp`). Fetch interception in our LoaderStrategy. SharedWorker like WebSharedWorkerServer. Soft update like ServiceWorkerSoftUpdateLoader, patch 0033 lets the SWServer recognize its own jobs. `WindowClient.navigate()` ends with the frame load. Preload and `openWindow` see #154 | Many sites and all PWAs use service workers. WebCore has everything, only the process connections were missing. Not yet: Push, Background Fetch. `WindowClient.focus()` see #169 |
| 104 | Background image decoding | One shared thread for all images instead of a WorkQueue per image (patch 0024) | Each new thread needs a Web Worker with the whole WASM module and the caller waits for it. A bigger pool (16) brought nothing measurable, so 8 stays |
| 105 | Persistent Cache API and service workers | Cache API: one file per origin under `/data/cachestorage` in WebKit's CacheStorageDiskStore format, at most 256 MB per origin (`put`/`addAll` all or nothing); bodies see #155. Service workers: WebCore's `SWRegistrationDatabase` under `/data/serviceworkers`; navigations wait for the import of their origin's registrations like WebKit2 | PWAs work offline again after a browser restart. Clearing data empties `/data` and with it this |
| 106 | Polyfill bridge | Hidden function `__blHost` that only the polyfill script sees (deleted before the first page script). The host runs a fixed list of host APIs (now the services of `@browser-lite/core`): EyeDropper, `navigator.getBattery`, `navigator.keyboard` | WebKit lacks these APIs, Chromium has them. The page is a canvas in the host, so the host's eyedropper works directly. Yardstick 239 of 277 |
| 107 | WebCodecs | `ENABLE_WEB_CODECS` on. Each page codec gets a real host codec in the engine worker (`engine/src/media/WebCodecsWasm.cpp`, `engine/js/webcodecs-host.js`); calls from workers go to the engine thread. Own `VideoFrame` with pixels in engine memory (I420, I420A, I422, I444, NV12, RGBA/BGRA), YUV -> RGB by color matrix and range; patch 0026 removes WebCore's empty placeholders | Video editors, conferencing and games use WebCodecs. The host codecs cover everything Chrome can (VP8/VP9/AV1/H.264, Opus/AAC/FLAC) without codecs in WASM. Yardstick 241 of 277 |
| 108 | Speech recognition | `webkitSpeechRecognition` with an own `SpeechRecognitionProvider` (`engine/src/DeviceClients.cpp`): the engine asks for the microphone per origin like Chrome, the host recognizes with its `SpeechRecognition` and reports back | Dictation and voice search work. WebKit has the API, only the recognizer was missing. Yardstick 242 of 277 |
| 109 | Printing | WebCore's `PrintContext` breaks the page with `@media print` into A4 pages (1 cm margin, layout in CSS px like Chrome), Skia's PDF backend makes a PDF (`engine/src/Printing.cpp`, like WebKitGTK); the view gets a `print` event. An almost empty last page is dropped | The host's print dialog prints real pages instead of a canvas screenshot. `beforeprint`/`afterprint` like Chrome, same page count as Chrome in the test |
| 110 | LTO | No `-flto=thin` | Built all of WebKit with ThinLTO and measured: CNN, Wikipedia and GitHub load equally fast (16.5-17.7 s, 5.5-6.4 s, 2.5-2.9 s), the micro benchmark (JS, DOM, parser, style) is equal or worse, the .wasm 8 MB bigger. While loading the engine waits only about 0.2 s for new threads (WorkQueues), the rest is computation in WebCore and JSC |
| 111 | Sound in the tab | The engine reports `isPlayingMediaDidChange` (Web Audio and media elements), views can be muted (`Page::setMuted`) | Like Chrome: see which tab plays sound and mute it without leaving the page |
| 112 | File System Access | `showOpenFilePicker`, `showSaveFilePicker`, `showDirectoryPicker` as a polyfill over the host bridge: the real Chrome handles stay in the host, the page gets objects with the prototypes of WebKit's handles and only a random id, valid only for the origin that got it. Contents go as Base64; a dropped open writable is aborted by a `FinalizationRegistry`; handles belong to their view | Web apps like vscode.dev, Excalidraw and Squoosh open and save real files like in Chrome |
| 113 | Camera, microphone, screen | `ENABLE_MEDIA_STREAM` (and `MEDIA_RECORDER`) on. Own factories, devices and sources (`engine/src/media/MediaStreamWasm.cpp`, patch 0027): a starting source opens the host device and hands the `ReadableStream` of a `MediaStreamTrackProcessor` directly to the engine worker; frames become `VideoFrameWasm`, sound goes as Float32 to WebCore. Prompt per origin like Chrome, device names only after permission. `srcObject` shows the newest frame, Web Audio gets the microphone through an own `AudioSourceProvider` | Video chats, QR scanners, dictation, screen recording with WebCodecs. No pixel goes through the main thread. Yardstick 245 of 277 |
| 114 | MediaRecorder | Own `MediaRecorderPrivate` (`engine/src/media/MediaRecorderWasm.cpp`, patch 0027). Frames and sound go raw to the engine worker, the host's `VideoEncoder`/`AudioEncoder` encode (VP8, VP9, AV1, Opus) and a small WebM writer in JS (`engine/js/mediarecorder-host.js`) muxes like Chrome. Types like Chrome, no MP4. `MediaStreamAudioDestinationNode` now delivers sound | The host `MediaRecorder` does not exist in workers and a detour through the main thread costs more. WebCodecs is there already. Yardstick 246 of 277 |
| 115 | Cheaper WebGL context switches | All WebGL contexts share a host context (patch 0016). Extensions and limits are queried once per host context, uniform buffers and constant vertex attributes are read only when set since the last restore. Switch WebGL 2: 32 -> 8.6 ms, new context 33 -> 9.6 ms | Pages with several canvases and fingerprint scripts blocked the engine. No queries at all would need a full shadow copy of all GL setters, too error prone |
| 116 | Known: forced layout in nested flexboxes | On 20min.ch changing `span.style` and reading `offsetLeft` costs 45-52 ms (Chromium 0.07 ms): WebKit relayouts flex items with percentage heights on every container layout (FIXME in WebKit). Chromium has a layout cache | Not changed: an own cache would also have to cover stretching and could bring layout bugs we cannot see without WebKit's layout tests. Safari behaves the same |
| 117 | WebRTC through the host (stage 1: data channels) | Instead of libwebrtc a polyfill (`engine/src/WebRTCPolyfill.cpp`): `RTCPeerConnection`, `RTCDataChannel` and friends with Chrome's API. Every connection has a real counterpart in the host (`packages/core/src/services/webrtc.ts`); events by long polling, states mirrored with sequence numbers. Connections belong to their origin, orphans close after 60 s | File transfer, games, WebTorrent work, also with normal Chrome peers. The network is the host's, not the relay (peers see the device IP), hence opt-in (#204) |
| 118 | WebRTC stage 2: media | `addTrack`, `addTransceiver`, `removeTrack`, senders, receivers, transceivers (`replaceTrack`, `setParameters`, `direction`, `stop`, `getStats`), `ontrack` with streams as in the SDP. Sending: camera and microphone go out as a copy of the real host track (no detour through the engine); other tracks (canvas, Web Audio, video) are written by an engine sink into a host `MediaStreamTrackGenerator` (WritableStream straight to the engine worker). Receiving: the peer's track flows through a `MediaStreamTrackProcessor` into a new engine source, the page gets a normal `MediaStreamTrack` (hidden media bridge only for the polyfill). Chrome delivers WebRTC sound only while it is played: a muted host `<audio>` keeps it flowing | Video calls (Meet, Jitsi, Discord) need exactly this. Tested both ways against a real Chromium page.
